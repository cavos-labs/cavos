**What is an embedded wallet?** An **embedded wallet** is a crypto wallet that lives inside an application. The user does not install anything. They sign in the way they already sign in to software, and the app provisions an on-chain account they can receive, pay, and sign with.

That is the developer definition. Embedded names where the wallet appears and who provisions it. It does not name who can produce a signature. The full product and SDK page is [embedded wallet](/embedded-wallet): custody, key models, and how to choose, including the [embedded wallet SDK](/embedded-wallet) section. The rest of this post explains the parts, so you can tell [embedded wallets](/embedded-wallet) apart and ask vendors the right questions.

## Embedded wallet, defined in three parts

An embedded wallet has three properties. A product needs all three to fit the term.

1. **It is provisioned by the app.** The wallet is created or looked up as part of the app's own sign-in, not by a separate download.
2. **Approval happens in the app's UI.** The user confirms a payment or a signature on a screen the product controls, not in a popup from a third-party extension.
3. **It is a real on-chain account.** The address can hold assets and sign transactions on the target chain. It is not a balance in the app's database.

The third point is what separates an embedded wallet from a custodial account balance at an exchange. The second is what separates it from a [browser extension](/blog/embedded-wallet-vs-browser-extension). [Embedded wallet vs smart wallet](/blog/embedded-wallet-vs-smart-wallet) is a different split: smart usually means a contract account, which can be embedded or not.

## How an embedded wallet works

The flow is the same across most providers:

- **Sign in.** The user authenticates with Google, Apple, email, or the app's existing login. This tells the system who the user is. It does not, by itself, authorize spending.
- **Resolve an address.** Given a stable user id, the wallet service returns the address for that user on that app and chain, or creates one.
- **Hold a signing key.** Somewhere, a private key or key shares can produce signatures for that address. Where that key lives is the most important design decision.
- **Sign and send.** When the user approves an action, the key signs and the transaction goes to the network. A sponsor often pays the fee.
- **Recover.** If the user changes devices, a recovery path restores the ability to sign on the new device.

Developers reach all of this through an [embedded wallet API](/blog/embedded-wallet-api), usually shipped as a client SDK. When the vendor runs the backend pieces for you, it is called [wallet as a service](/blog/wallet-as-a-service).

## Who holds the key

"Embedded" says where the wallet appears. It does not say who controls it. Three common key models:

| Model | Where the key lives | What to ask |
|---|---|---|
| Device key | Created and used on the user's device | How does a new device restore it? |
| MPC shares | Split between the device, the provider, and a recovery factor | Can the provider's share plus another factor sign without the user? |
| Provider enclave or HSM | In hardware the provider operates | Who can authorize that hardware to sign? |

A wallet is non-custodial when the provider cannot produce a valid signature on its own. The full test is in [non-custodial embedded wallets](/blog/non-custodial-embedded-wallet), and the legal side is on the [custody](/custody) page.

Device-native keys are the Cavos default: the account key is derived on the device from a MasterDEK, signing always happens on the device, and keys never leave the device in plaintext. MPC is a legitimate design; the provider usually holds a share used in reconstruction. A remote enclave or HSM is hosted signing unless the vendor cannot be asked to spend. [Privy vs Turnkey](/blog/privy-vs-turnkey) is the finished-SDK versus signing-infrastructure fork of that last row. The named-vendor table is [embedded wallet providers](/blog/embedded-wallet-providers).

## Embedded wallet vs browser extension

A [browser extension](/blog/embedded-wallet-vs-browser-extension) is software the user installs. The user controls the seed. Approval happens in a popup the product does not own. The dapp requests access; it does not create the account. That is the right default when users already hold wallets, move assets across many sites, or must connect an existing address.

An embedded wallet inverts that. Login selects the user. The SDK looks up or creates an on-chain account. Approval happens in your UI. There is no second program to install and no seed phrase to copy. The cost is portability: the wallet is product-scoped unless you also connect or export.

Many apps support both. Provision an embedded wallet for users who have never used crypto. Keep an extension connector for users who already arrive with one. Cavos does not connect existing extensions. If connecting MetaMask or WalletConnect is a requirement, a connection-focused provider is the better fit.

## Embedded wallet vs smart wallet

[Embedded wallet vs smart wallet](/blog/embedded-wallet-vs-smart-wallet) is a category error if you treat them as two products on a shelf. They answer different questions.

- **Embedded** is where the wallet appears and who provisions it.
- **Smart** is what the on-chain account is: usually a contract that can enforce policy, batch calls, or sponsor gas.

An embedded wallet can be a smart account. A browser extension can be a smart account too. Cavos on [Starknet](/embedded-starknet-wallet) is both: an in-app wallet whose on-chain account is an audited OpenZeppelin account contract (AccountUpgradeable v3.0.0). Cavos on [Solana](/embedded-solana-wallet) and [Stellar](/embedded-stellar-wallet) is embedded and native, not a contract wallet. Account abstraction does not decide custody. A paymaster or relayer is not a signer.

## Embedded wallet vs other wallets

| | Embedded wallet | Browser extension or wallet app | Exchange account |
|---|---|---|---|
| Install | None | User installs it | None |
| Where approval happens | Inside your app | In the extension or app | Inside the exchange |
| On-chain address per user | Yes | Yes | Usually pooled |
| Works across many sites | Usually one app | Yes | No |
| Seed phrase | Usually none | Usually yes | No |

Embedded wallets trade portability across sites for onboarding inside one product. Many apps support both: an embedded wallet for new users, and external wallet connections for users who already have one.

## When to use one

An embedded wallet fits when:

- Most of your users have never set up a crypto wallet.
- Sign-up should look like any other app's sign-up.
- On-chain actions such as payments, rewards, or ownership are a feature of the product, not the reason users came.
- You want users to transact before they hold the chain's fee token.

It is a weaker fit when your users already arrive with a wallet they use everywhere and expect to connect it.

Use Cavos when the product is Starknet, Solana, or Stellar and the review requires a device-native key. The free tier covers the first 1,000 wallets. Setup is minutes with `@cavos/kit` 0.5.2. It is the worse fit when you need broad EVM coverage or must connect MetaMask. The Stellar shortlist is [best embedded wallets for Stellar](/blog/best-embedded-wallets-stellar).

## A concrete example: Cavos

[Cavos](/) is an embedded wallet SDK for Starknet, Solana, and Stellar. It maps onto the definition above like this:

- **Provisioned by the app.** `Cavos.connect` looks up or claims the address for a user, app, chain, and network. Sign-in is Cavos-hosted (Google, Apple, email) or your own auth.
- **Key model.** Custody is hardware-isolated and non-custodial. The signing key is derived and used on the user's device. Keys never leave the device in plaintext. Signing always happens on the device. Cavos cannot see the key, sign with it, or move funds.
- **Recovery.** Another signed-in device, a synced passkey, or opt-in hardware-isolated recovery in an AWS Nitro Enclave. The passkey and the enclave only hold an encrypted copy of the MasterDEK for sealed restore. They cannot sign. Cavos cannot decrypt that copy. The enclave is open source at [cavos-labs/cavos-recovery](https://github.com/cavos-labs/cavos-recovery).
- **Native accounts.** On [Starknet](/embedded-starknet-wallet) the wallet is an audited OpenZeppelin account contract. On [Solana](/embedded-solana-wallet) it is a native Ed25519 account. On [Stellar](/embedded-stellar-wallet) it is a classic G account.
- **Fees.** Gas Sponsorship in Any Token, so a new user can transact without the chain's fee token.

```ts
import { Cavos } from "@cavos/kit";

const session = await Cavos.connect({
  chains: ["stellar"],
  defaultChain: "stellar",
  network: "testnet",
  appSalt: "my-app",
  identity: { userId: user.id, email: user.email },
  appId: process.env.NEXT_PUBLIC_CAVOS_APP_ID,
});

const wallet = session.wallet("stellar");
console.log(wallet.address); // the user's embedded wallet address
```
