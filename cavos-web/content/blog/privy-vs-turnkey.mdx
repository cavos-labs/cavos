An [embedded wallet](/embedded-wallet) lives inside your application. The user signs in the way they already do. The product resolves an on-chain account they can pay, receive, and sign with. **Privy vs Turnkey** is the question Search Console keeps sending at that category: one vendor is a finished auth and wallet product, the other is lower-level signing infrastructure. This guide is that comparison, product scope, key model, chains, developer experience, pricing, and who each is for.

## Product scope

The usual mistake is treating these as two SDKs with different logos. They sit at different layers.

**Privy** is a finished authentication and [embedded wallet](/embedded-wallet) product. The public pricing page lists unified login (email, SMS, socials, passkeys), embedded wallets, JWT-based authentication (Auth0, Firebase, or homegrown), and wallet connectors for EVM and Solana. Privy’s own embedded-wallet docs describe user wallets (no separate extension or mobile wallet app), organization and treasury wallets, agent wallets, and the option to connect external wallets such as MetaMask or Phantom. In 2026 Privy also documents optional [custodial wallets](https://docs.privy.io/wallets/custodial-wallets/overview) backed by Bridge, a Stripe company, chosen per wallet. Stripe [announced it was acquiring Privy](https://privy.io/blog/announcing-our-acquisition-by-stripe) in June 2025. Acquisition is a vendor-risk input. It does not change who can produce a signature.

**Turnkey** is key-management and signing infrastructure. Private keys persist as ciphertext and decrypt only inside a trusted execution environment. Turnkey’s [embedded-wallet overview](https://docs.turnkey.com/solutions/embedded-wallets/overview) is explicit that you are buying wallet infrastructure: authenticate a user, create keys, configure custodial, non-custodial, or hybrid custody, enforce a programmable policy engine, and get a signature back. You can broadcast through another provider or with Turnkey Transaction Management. The recommended React start is the Embedded Wallet Kit, pre-built auth and wallet UI, hook-based, no backend of your own. That kit does not turn Turnkey into Privy. The core surface is still the enclave, the policy engine, and the API.

Privy vs Turnkey is usually **build-versus-buy**, the same layer split as [wallet as a service](/blog/wallet-as-a-service) platforms. Buy Privy when login, an in-app wallet, and connectors should arrive as one product. Build on Turnkey when policy, quorums, and server-side signing primitives *are* the product.

## Abstractions vs signing primitives

Search Console also asks this as four questions. The answers are the same layer split, with chain coverage and flexibility filled in from each vendor’s public docs.

**How Privy’s higher-level product abstractions differ from lower-level signing and key-management primitives.** Privy wraps login, an in-app wallet, and connectors as one product. Turnkey exposes signing and key-management primitives: authenticate, create keys in a TEE, set policy, return a signature. Privy’s abstractions hide auth, wallet create, and (on managed-send chains) broadcast. Turnkey’s primitives stop at a signature unless you add Transaction Management or the Embedded Wallet Kit.

**How Privy’s product scope compares with Turnkey’s focus on low-level signing infrastructure.** Privy’s public surface is unified login, embedded wallets, JWT auth, and connectors for MetaMask or Phantom. Turnkey’s [embedded-wallet overview](https://docs.turnkey.com/solutions/embedded-wallets/overview) names that wallet infrastructure. Scope is build-versus-buy, not two SDKs with different logos.

**Architecture, “MPC,” and adding chains or curves.** Privy does not document TSS-MPC. [Security architecture](https://docs.privy.io/security/wallet-infrastructure/architecture) describes AWS Nitro Enclaves plus Shamir 2-of-2 key sharding; Privy’s public security page contrasts Shamir sharing with TSS-based MPC. New chains follow Privy’s published tiers (managed send, sign-transaction, or sign-only) so you wait for Privy to list the network at the depth you need. Turnkey [signs at the curve](https://docs.turnkey.com/features/networks/overview) (secp256k1, Ed25519, P-256) and states you do not wait for a per-network integration to sign if the curve is supported. Address derivation, SDK construction, and transaction-aware policy are still a shorter published list.

**Does Turnkey’s lower-level model necessarily mean more flexibility?** No. Turnkey is more flexible at custody configuration, policy, quorums, server-side signing, and curve-level coverage. Privy is more flexible as a finished product: one vendor for login, an in-app wallet, and connecting wallets users already hold, plus managed send on EVM and Solana. The Embedded Wallet Kit shortens Turnkey’s React start. It does not add Privy’s connector suite.

## Key model and custody

Write down who can produce a valid signature without the user present. The [custody](/custody) page is the control test. This section is what each vendor publishes.

**Privy** combines TEEs with distributed key sharding. Official security docs say Privy uses AWS Nitro Enclaves; keys exist as encrypted shares; shares are combined only inside the enclave. A wallet is a 2-of-2 Shamir split: an enclave share that can be decrypted only in the TEE, and an auth share that Privy stores encrypted and releases with valid authentication credentials. Privy’s [user-wallet docs](https://docs.privy.io/wallets/overview/embedded) say neither Privy nor the application sees the user’s keys on that path; secrets are reconstituted in a secure environment under the user’s control. Users can export the key. Separately, Privy ships **custodial** wallets backed by a licensed custodian (today Bridge) on the same authorization and policy framework.

**Turnkey** never returns the private key as part of signing. Official docs: keys live in TEEs; derivation and signing happen inside verifiable infrastructure; only the signature leaves. [Custody is who holds the credentials](https://docs.turnkey.com/solutions/embedded-wallets/overview) that can authorize the enclave:

- **Non-custodial.** Only the user’s authenticator (passkey, email, biometric) can authorize a signature. Users can export keys.
- **Custodial.** Your application holds signing authority via API key and can authorize transactions without per-action user approval.
- **Hybrid.** Both hold credentials; policy decides what each party can authorize.

Turnkey recommends a sub-organization per end user so wallets, credentials, and policies stay isolated. Import and export are documented. A breach of your app or backend is not supposed to expose key material; the enclave still has to approve the request.

Neither design is device-native in the Cavos sense. Both reconstruct or use a key inside an enclave the vendor operates. The difference is product wrapping (Privy) versus policy-gated primitives (Turnkey), plus Privy’s optional licensed-custodian path.

## Developer experience

**Privy** is the shorter path to a consumer wallet in a React or mobile app. You get hosted or JWT login, an embedded wallet bound to that user, optional connectors for wallets they already hold, UI components or bare APIs, and SDKs listed for web, mobile, and gaming. Pregenerating a wallet for an email or phone before first login is documented. Export is the documented escape hatch. You are integrating a product.

**Turnkey** is the shorter path to policy-gated keys. Every sensitive operation is an authenticated request the enclave evaluates. Auth includes passkeys / WebAuthn, email or SMS OTP, OAuth (Google, Apple, Twitter, Discord, GitHub, LinkedIn, and others), API keys, and sign-in with an external Ethereum or Solana wallet. Client SDKs exist for React (Embedded Wallet Kit), React Native, Swift, Kotlin, and Flutter; fully custom work calls the API. Gas sponsorship is listed on Turnkey’s public pricing page as an Enterprise feature. You are integrating infrastructure, even when you start from the kit.

Time-to-first-signature is not the same as time-to-product. Privy collapses login, wallet, and connectors. Turnkey collapses key lifecycle, policy, and signing; auth and UI are available, but broadcast, recovery UX, and chain adapters are still your design unless you adopt Transaction Management and the kit.

## Turnkey vs Privy vs Dfns

Search Console also asks this as a three-vendor shortlist. The vendors are not interchangeable SDKs. They sit at different layers.

**Privy** is the finished product: unified login, an in-app wallet, and connectors for wallets users already hold. Keys are a Shamir 2-of-2 reconstructed inside AWS Nitro Enclaves. New chains follow Privy’s published send / sign-transaction / sign-only tiers.

**Turnkey** is enclave signing infrastructure. The key decrypts only inside a TEE. Custody is who holds the credentials that can authorize that enclave: the user, your API key, or both under policy. Signing is at the cryptographic-curve level; you assemble more of the wallet experience, or start from the Embedded Wallet Kit.

**Dfns** is MPC wallet infrastructure. Official [MPC docs](https://docs.dfns.co/core-concepts/how-mpc-wallets-work) describe a threshold signature scheme: key shares participate in a ceremony and the private key is never reconstructed. In the default cloud, Dfns stores all shares in its geographically distributed datacenters, unlike providers that give a shard to the user. [Delegated wallets](https://docs.dfns.co/advanced/delegated-wallets) keep those shares in the Dfns network; they are not stored on the user’s device. The user’s passkey is the signing credential. Org-managed wallets stay under your service account. [Embed user wallets](https://docs.dfns.co/solutions/embed-user-wallets) is that delegated path. Policies do not apply to delegated wallets. Recovery is something you implement; Dfns cannot restore a wallet if the only passkey is gone. Signer deployments also include [hybrid and on-premise](https://docs.dfns.co/advanced/deployment-models/mpc) options; Dfns recommends a 3-out-of-5 threshold. A single key can power wallets on multiple supported networks, including Ethereum, Bitcoin, and Solana. This page does not invent unpublished Dfns pricing.

None of the three is a device-native key on the user’s device. That is a different product shape.

## Who each is best for

**Choose Privy** when the user should get an in-app wallet from a login you already understand, and you also need to connect MetaMask, Phantom, or WalletConnect for people who already hold assets. EVM-first consumer apps, games, and anything that wants one vendor for auth plus wallet sit here. The optional Bridge custodial path matters if counsel wants a licensed custodian on some wallets and a non-custodial embedded wallet on others.

**Choose Turnkey** when you are building the wallet or the custody layer. Server-side signing, organizational quorums, per-user sub-organizations, and a policy engine that runs inside the enclave are the reason to pick it. The Embedded Wallet Kit is there if you want a faster React start; it does not remove the need to own broadcast, chain semantics, and recovery UX if you go below that kit.

**Choose neither** when the requirement is a device-native key on Starknet, Solana, or Stellar, or when the review says the vendor must not be able to reconstruct a signing key in its infrastructure. That is a different product shape. The next section is that shape, not a third row pretending to be the same layer.

## Where Cavos fits

Cavos is a hardware-isolated, non-custodial [embedded wallet](/embedded-wallet), not an extension, and not signing infrastructure.

Signing keys are created and used on the user’s device. Cavos cannot see them, sign with them, or move funds. Login produces a stable identity for a registry lookup; it never signs a transaction. There is no MPC. There is no hosted spend key.

On Starknet the on-chain account is an **audited OpenZeppelin account contract** (AccountUpgradeable v3.0.0), controlled by one stark key derived from the wallet’s MasterDEK and app salt. Cavos does not ship its own account implementation. There is no on-chain device-signer list and no on-chain social recovery. A new device restores the MasterDEK off-chain with a passkey or an opt-in AWS Nitro Enclave; it does not add a signer on-chain. Execution is paymaster-sponsored. Connect does not deploy, the first execute deploys and runs atomically.

Solana and Stellar are native adapters, not EVM compatibility. Solana provisions a native Ed25519 system account; a relayer co-signs as fee payer. Stellar provisions a classic G… account so existing tools already understand the address; the relayer can sponsor reserves and fee-bumps. Both restore the same MasterDEK on a new device rather than adding a second on-chain signer.

Auth is hosted Google, Apple, or email, or an identity you pass in from your own stack. The React path is `@cavos/kit`; mobile is `@cavos/kit/react-native`. The current kit release is [Cavos Kit 0.5.0](/blog/cavos-kit-0-5-0). [Pricing](/pricing) publishes the free 1,000 wallet creates, Essential at $59/mo, and Complete at $139/mo.

**Choose Cavos** when the user should never see a wallet picker, the chain is Starknet, Solana, or Stellar, and the review requires that the vendor cannot reconstruct a signing key.

**Stay with Privy or Turnkey** when the product is EVM-first, when you must connect an existing extension, when you need server-side signing or organizational quorums as a product feature, or when you want a single vendor across dozens of EVM networks. Cavos does not inject into `window.ethereum` and does not speak WalletConnect. Those are honest gaps, not a smaller feature set.
