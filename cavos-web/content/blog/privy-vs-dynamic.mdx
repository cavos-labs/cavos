An [embedded wallet](/embedded-wallet) lives inside your application. The user signs in the way they already do. The product resolves an on-chain account they can pay, receive, and sign with. **Privy vs Dynamic** is a product-shape question, not a layer question: both ship login and an in-app wallet. The fork is **provision versus connect**. Teams also type **Privy vs Dynamic vs Turnkey for embedded wallets**. Turnkey sits on a different layer. This guide is the two-way, with a short three-way note.

## Decision: Privy vs Dynamic vs Turnkey

**Privy vs Dynamic** is provision versus connect. **Privy vs Dynamic vs Turnkey** adds a layer question: two finished SDKs versus signing infrastructure.

- **Choose Privy** when login should mint an in-app wallet, with connectors available, especially on EVM managed send.
- **Choose Dynamic** when connecting wallets users already hold is first-class, with a TSS-MPC embedded fallback.
- **Choose Turnkey** when you are buying keys, policy, and a signature, then assembling the wallet yourself. That write-up is [Privy vs Turnkey](/blog/privy-vs-turnkey).
- **Choose neither** when the chain is Starknet, Solana, or Stellar and the review requires a hardware-isolated, non-custodial device key. Cavos signs on the device, cannot reconstruct a signing key, and is free to 1,000 wallets. See [pricing](/pricing).

## Product scope

The usual mistake is treating these as two logos on the same SDK. They wrap the same job differently.

**Privy** is a finished authentication and [embedded wallet](/embedded-wallet) product. The public pricing page lists unified login (email, SMS, socials, passkeys), [embedded wallets](/embedded-wallet), JWT-based authentication (Auth0, Firebase, or homegrown), and wallet connectors for EVM and Solana. Privy’s [user-wallet docs](https://docs.privy.io/wallets/overview/embedded) describe wallets with no separate extension or mobile wallet app, plus organization, treasury, and agent wallets, and the option to connect external wallets such as MetaMask or Phantom. In 2026 Privy also documents optional [custodial wallets](https://docs.privy.io/wallets/custodial-wallets/overview) backed by Bridge, a Stripe company, chosen per wallet. Stripe announced it was acquiring Privy in June 2025. Acquisition is a vendor-risk input. It does not change who can produce a signature.

**Dynamic** is a unified login and wallet-connection layer that also ships [embedded wallets](/embedded-wallet). [Embedded-wallet docs](https://www.dynamic.xyz/docs/embedded-wallets/mpc/overview) describe a programmable in-app wallet issued inside your site or app, plus connecting wallets the user already holds. Connecting existing external wallets is a core capability, not an add-on. Embedded wallets are TSS-MPC. Smart accounts, gas abstraction, and developer-managed (agentic) MPC wallets are documented separately; those agentic wallets are not end-user owned. Fireblocks acquired Dynamic in 2025. Acquisition is a vendor-risk input. It does not change who can produce a signature.

Privy vs Dynamic is usually **provision versus connect**, the same fork as [wallet as a service](/blog/wallet-as-a-service) platforms that also speak WalletConnect. Buy Privy when login and an in-app wallet should arrive as one product, with connectors available. Buy Dynamic when the product must connect wallets users already hold, with an embedded TSS-MPC fallback.

## Key model and custody

Write down who can produce a valid signature without the user present. The [custody](/custody) page is the control test. This section is what each vendor publishes.

**Privy** combines TEEs with distributed key sharding. Official [security architecture](https://docs.privy.io/security/wallet-infrastructure/architecture) docs say Privy uses AWS Nitro Enclaves; keys exist as encrypted shares; shares are combined only inside the enclave. A wallet is a 2-of-2 Shamir split: an enclave share that can be decrypted only in the TEE, and an auth share that Privy stores encrypted and releases with valid authentication credentials. Privy does not document TSS-MPC; the public security page contrasts Shamir sharing with TSS-based MPC. User-wallet docs say neither Privy nor the application sees the user’s keys on that path; secrets are reconstituted in a secure environment under the user’s control. Users can export the key. Separately, Privy ships **custodial** wallets backed by a licensed custodian (today Bridge) on the same authorization and policy framework.

**Dynamic** documents [TSS-MPC](https://www.dynamic.xyz/docs/embedded-wallets/mpc/overview). Official copy: a complete private key never exists in one place or is held by a single party. The default [configuration](https://www.dynamic.xyz/docs/embedded-wallets/mpc/configuration-guide) is 2-of-2: a user share stored locally on the device (on web, in an iframe) and a Dynamic server share that participates in signing inside a TEE. Dynamic’s architecture page states the complete private key never exists, even inside the TEE. Users can enable password encryption and store a share in published backup options. 2-of-3 (and other schemes such as 3-of-5, contact Dynamic) is documented. Embedded wallets can be exported. Dynamic also documents developer-managed 2-of-2 MPC wallets that are not end-user owned; those are a different product path.

Neither design is device-native in the Cavos sense. Privy reconstitutes a key inside an enclave it operates. Dynamic jointly computes a signature with a vendor-held server share. The difference is Shamir reconstruction (Privy) versus threshold signatures (Dynamic), plus Dynamic’s first-class connector surface and Privy’s optional licensed-custodian path.

## Developer experience

**Privy** is the shorter path to a consumer in-app wallet in a React or mobile app. You get hosted or JWT login, an embedded wallet bound to that user, optional connectors, UI components or bare APIs, and SDKs listed for web, mobile, and gaming. Pregenerating a wallet for an email or phone before first login is documented. Export is the documented escape hatch. You are integrating a product whose center of gravity is the embedded wallet.

**Dynamic** is the shorter path to a login that can both provision and connect. Dashboard configuration of chains, wallets, and the auth experience is a published strength. Embedded wallets can be created automatically on sign-in or manually in app logic. Connectors for wallets users already hold are first-class. You are integrating a connection layer that also embeds.

Time-to-first-signature is not the same as time-to-product. Both collapse login and wallet create. Dynamic also collapses wallet discovery. Privy collapses managed send on EVM and Solana.

## Who each is best for

**Choose Privy** when the user should get an in-app wallet from a login you already understand, and you also need to connect MetaMask, Phantom, or WalletConnect for people who already hold assets. EVM-first consumer apps, games, and anything that wants one vendor for auth plus wallet sit here. The optional Bridge custodial path matters if counsel wants a licensed custodian on some wallets and a non-custodial embedded wallet on others.

**Choose Dynamic** when users already hold wallets you must connect, or when you want that connector surface plus an embedded TSS-MPC fallback, especially if Dynamic’s JS/React Tier 1 list (Stellar, Sui, Bitcoin, TON, Aleo, Midnight, and the rest) matches the chains you ship. Stay with Privy when managed send on EVM and Solana, or a licensed-custodian option, is the constraint.

**Choose Turnkey** when you are building the wallet or the custody layer. Server-side signing, organizational quorums, per-user sub-organizations, and a policy engine that runs inside the enclave are the reason to pick it. That is not the Privy vs Dynamic fork.

**Choose neither** when the requirement is a device-native key on Starknet, Solana, or Stellar, or when the review says the vendor must not be able to reconstruct a signing key in its infrastructure. That is a different product shape. The next section is that shape, not a fourth row pretending to be the same layer.

## Where Cavos fits

Cavos is a hardware-isolated, non-custodial [embedded wallet](/embedded-wallet), not an extension, and not a connector.

Signing keys are created and used on the user’s device. Private keys never leave the device in plaintext. Signing always happens on the user’s device. Cavos cannot see them, sign with them, or move funds. Login produces a stable identity for a registry lookup; it never signs a transaction. There is no MPC. There is no hosted spend key. The Nitro enclave and passkey only store an encrypted copy of the master key for restore.

On Starknet the on-chain account is an **audited OpenZeppelin account contract** (AccountUpgradeable v3.0.0), controlled by one stark key derived from the wallet’s MasterDEK and app salt. Cavos does not ship its own account implementation. There is no on-chain device-signer list and no on-chain social recovery. A new device restores the MasterDEK off-chain with a passkey or an opt-in AWS Nitro Enclave; it does not add a signer on-chain. Execution is paymaster-sponsored. Connect does not deploy, the first execute deploys and runs atomically.

Solana and Stellar are native adapters, not EVM compatibility. Solana provisions a native Ed25519 system account; a relayer co-signs as fee payer. Stellar provisions a classic G… account so existing tools already understand the address; the relayer can sponsor reserves and fee-bumps. Both restore the same MasterDEK on a new device rather than adding a second on-chain signer.

Auth is hosted Google, Apple, or email, or an identity you pass in from your own stack. The React path is `@cavos/kit`; mobile (`@cavos/kit/react-native`) is a work in progress. The current kit release is [Cavos Kit 0.5.2](/blog/cavos-kit-0-5-2). The open-source recovery enclave shipped in [Cavos Kit 0.5.0](/blog/cavos-kit-0-5-0). [Pricing](/pricing) publishes the free 1,000 wallet creates, Essential at $59/mo, and Complete at $139/mo.

**Choose Cavos** when the user should never see a wallet picker, the chain is Starknet, Solana, or Stellar, and the review requires that the vendor cannot reconstruct a signing key.

**Stay with Privy or Dynamic** when the product is EVM-first, when you must connect an existing extension, or when you want a single vendor across Dynamic’s or Privy’s published EVM lists. Cavos does not inject into `window.ethereum` and does not speak WalletConnect. Those are honest gaps, not a smaller feature set.

This page is not [Cavos vs Dynamic](/compare/dynamic). That page is the one-to-one with Cavos. This page is Privy vs Dynamic.
