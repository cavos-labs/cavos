An [embedded wallet](/embedded-wallet) lives inside your application. **Alchemy vs Privy** is the question Search Console keeps sending at that category, and it is easy to treat them as two SDKs with different logos. They are not. Alchemy’s wallet offering is a transaction layer after Account Kit’s deprecation. Privy is a finished auth and wallet product, and Alchemy’s own docs recommend it as the signer.

This guide is Alchemy vs Privy, not a Privy alternatives shortlist. The replacement list is [Privy alternatives](/privy-alternatives). Cavos, LLC is a software and SaaS company. Positioning for Cavos comes after the table is fair. If the honest answer is Alchemy Wallet APIs plus Privy, that is the answer. ## Product scope

The usual mistake is a like-for-like SDK swap. Alchemy vs Privy is **transaction layer versus signer**.

**Alchemy.** Account Kit (v4), including embedded wallets, signer support, and key management (React SDK, embedded UI, login methods), is deprecated. Wallet APIs are the supported successor. They are signer-agnostic: you bring a signer for login and keys; Wallet APIs sponsor gas, batch calls, retry stuck transactions, and upgrade an existing EOA to a smart wallet with EIP-7702. New sign-ups for the Alchemy Signer, Account Kit, and Embedded Wallets have been turned off since 18 June 2026. Login and auth endpoints remain live so existing users can sign in and migrate.

**Privy** is a finished authentication and embedded wallet product. The public pricing page lists unified login (email, SMS, socials, passkeys), embedded wallets, JWT-based authentication (Auth0, Firebase, or homegrown), and wallet connectors for EVM and Solana. Privy’s user-wallet docs describe wallets with no separate extension, plus the option to connect MetaMask or Phantom. In 2026 Privy also documents optional custodial wallets backed by Bridge, a Stripe company. Stripe announced it was acquiring Privy in June 2025. Acquisition is a vendor-risk input. It does not change who can produce a signature.

Alchemy’s deprecation page is explicit: use Wallet APIs for new integrations, and **recommend Privy or another provider for signer support** alongside those APIs. Wallet APIs also document Turnkey, Openfort, and any viem-compatible signer. Signers that cannot sign EIP-7702 authorizations use non-7702 mode, which creates a separate smart wallet address.

Buy Privy when login, an in-app wallet, and connectors should arrive as one product. Add Alchemy Wallet APIs when you already have that signer and want EVM (and Solana) gas sponsorship, batching, and EIP-7702 on top.

## Key model and custody

Write down who can produce a valid signature without the user present. The [custody](/custody) page is the control test.

**Alchemy Wallet APIs** do not hold the user’s signing key. Login and keys belong to the signer you bring. Recovery is not provided by Wallet APIs; it belongs to Privy, Turnkey, or whichever signer you chose. EIP-7702 is the default account path: the EOA delegates to Modular Account v2 without changing address.

**Privy** combines TEEs with distributed key sharding. Official security docs say Privy uses AWS Nitro Enclaves; a wallet is a 2-of-2 Shamir split reconstituted inside the enclave. Privy’s user-wallet docs say neither Privy nor the application sees the user’s keys on that path, and users can export the key. Separately, Privy ships custodial wallets backed by Bridge on the same authorization framework.

Neither design is device-native in the Cavos sense. Privy reconstructs or uses a key inside an enclave it operates. Alchemy leaves that question to the signer.

## Chains supported

**Alchemy Wallet APIs** document gas sponsorship on many EVM networks and on Solana. Bundler, ERC-20 gas payments, and Bundler Sponsored Operations are documented for those EVM networks, not for Solana. Solana gets fee and rent sponsorship without a bundler. Feature parity still varies by network. Read Alchemy’s current supported-chains page before you promise a chain.

The practical fork: Privy is stronger when you want **managed send** on EVM and Solana, plus connectors. Alchemy Wallet APIs are stronger when you already have a signer and want **sponsored execution, batching, and EIP-7702** across a long EVM list.

## Developer experience

**Privy** is the shorter path to a consumer wallet in a React or mobile app. You get hosted or JWT login, an embedded wallet bound to that user, optional connectors, and SDKs listed for web, mobile, and gaming. You are integrating a product.

**Alchemy Wallet APIs** are the shorter path to a transaction layer. You prepare calls, the signer signs, Wallet APIs submit, sponsor, bump fees, and track status. The TypeScript SDK and REST APIs are both documented. You still own login, key custody, and recovery unless Privy (or another signer) supplies them. Account Kit’s React SDK, embedded UI, and login methods are the deprecated path, do not start there.

Time-to-first-signature is not the same as time-to-product. Privy collapses login, wallet, and connectors. Alchemy collapses sponsorship and smart-wallet execution; the signer is a second vendor.

## Who each is best for

**Choose Privy** when the user should get an in-app wallet from a login you already understand, and you also need to connect MetaMask, Phantom, or WalletConnect for people who already hold assets. EVM-first consumer apps sit here. Alchemy’s own docs put Privy in this seat as the recommended signer when you add Wallet APIs.

**Choose Alchemy Wallet APIs** when you already have a signer (Privy, Turnkey, Openfort, or a viem-compatible key) and want gas sponsorship, batching, session keys, and EIP-7702 Modular Account v2 on many EVM networks (and Solana sponsorship without a bundler). Do not choose Account Kit for a new integration; it is deprecated.

**Choose both** when that is the documented architecture: Privy (or another signer) for login and keys, Wallet APIs for the transaction layer. That is Alchemy’s recommended path, not a competition between two embedded-wallet SDKs.

**Choose neither** when the requirement is a device-native key on Starknet, Solana, or Stellar, or when the review says the vendor must not be able to reconstruct a signing key in its infrastructure. The next section is that shape.

## Where Cavos fits

Cavos is an [embedded wallet](/embedded-wallet), not an extension, not a connector, and not a transaction layer you pair with a separate signer.

Signing keys are created and used on the user’s device. Cavos cannot see them, sign with them, or move funds. Login produces a stable identity for a registry lookup; it never signs a transaction. There is no MPC. There is no hosted spend key.

On Starknet the on-chain account is an **audited OpenZeppelin account contract** (AccountUpgradeable v3.0.0). Cavos does not ship its own account implementation. There is no on-chain device-signer list and no on-chain social recovery. Execution is paymaster-sponsored. Connect does not deploy, the first execute deploys and runs atomically.

Solana and Stellar are native adapters. Solana provisions a native Ed25519 system account; a relayer co-signs as fee payer. Stellar provisions a classic G… account; the relayer can sponsor reserves and fee-bumps. Both restore the same MasterDEK on a new device rather than adding a second on-chain signer.

Auth is hosted Google, Apple, or email, or an identity you pass in from your own stack. The React path is `@cavos/kit`; mobile is `@cavos/kit/react-native`. [Pricing](/pricing) publishes Free up to 1,000 wallets, Essential at $59/mo, and Complete at $139/mo.

**Choose Cavos** when the user should never see a wallet picker, the chain is Starknet, Solana, or Stellar, and the review requires that the vendor cannot reconstruct a signing key.

**Stay with Privy, or with Alchemy Wallet APIs plus a signer,** when the product is EVM-first, when you must connect an existing extension, or when you want a transaction layer across dozens of EVM networks. Cavos does not inject into `window.ethereum` and does not speak WalletConnect. Those are honest gaps, not a smaller feature set.
