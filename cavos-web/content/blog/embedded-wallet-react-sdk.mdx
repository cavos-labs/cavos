An [embedded wallet](/embedded-wallet) lives inside your application. Search **best practices for embedding a wallet SDK in an app** and you want decisions, not another copy of `npm install`: who holds the key, when to enroll a passkey, how gas is paid, which errors are first-class, and what differs on Starknet, Solana, and Stellar.

This page is that companion for `@cavos/kit` 0.5.2. The first install is [how to add an embedded wallet](/blog/how-to-add-an-embedded-wallet). The App Router wiring is [how to add an embedded wallet to Next.js](/blog/embedded-wallet-nextjs). The method map is the [embedded wallet API](/blog/embedded-wallet-api). Code follows the same contract as the [Cavos React docs](https://docs.cavos.xyz/docs/react) and [quickstart](https://docs.cavos.xyz/docs/quickstart): authenticate, connect, then execute. For platform parts, pricing models, and build versus buy, see [wallet as a service](/blog/wallet-as-a-service).

Cavos, LLC is a software and SaaS company. The wallet is the main product: a hardware-isolated, non-custodial [embedded wallet](/embedded-wallet). Signing always happens on the user’s device. Keys never leave the device in plaintext and are never used for signing on servers. The enclave and passkey only store an encrypted copy of the master key for restore. Cavos cannot see the key, sign with it, or move funds. Adapters ship today for [Starknet](/embedded-starknet-wallet), [Solana](/embedded-solana-wallet), and [Stellar](/embedded-stellar-wallet). [Pricing](/pricing) publishes Free up to 1,000 wallets, Essential at $59/mo, and Complete at $139/mo.

## Kit 0.5.2 practices

Pin the current kit when an install line appears:

```bash
npm install @cavos/kit@^0.5.2
```

The React bindings live on the same package, under `@cavos/kit/react`. You do not install a second library. Telegram as a hosted login needs 0.5.2; see [Sign in with Telegram (Kit 0.5.2)](/blog/cavos-kit-0-5-2). Kits 0.5.0 and 0.5.1 still work for Google, Apple, email, and GitHub against the current enclave. 0.4.x does not.

Telegram on web is **optional OAuth** through `https://oauth.telegram.org/auth`. It is not a Telegram Mini App. Add `'telegram'` to `modal.providers`, or call `login("telegram")` from `useCavos()`. The default modal providers stay Google, Apple, and email until you add it.

GitHub (since 0.5.0) is the same shape: optional, web only, add `'github'` to `modal.providers` or call `login("github")`.

`openModal()` opens the hosted flow. `login("google")` and `login("apple")` start OAuth. `sendOtp(email)` / `verifyOtp(email, code)` cover email (9-character code). On the enclave (`deviceApproval: "enclave"`, the default with `socialRecovery`) the modal uses a magic link: an email OTP yields no token the recovery enclave accepts.

React Native cannot run Telegram, email, or GitHub. That build cannot verify enclave attestation. Details are in [React Native limits](#react-native-limits) below.

## Device-native signing

Write down who can produce a valid signature without the user present. That is the [non-custodial](/blog/non-custodial-embedded-wallet) test, not the login modal.

In Cavos a non-exportable key is created on the device. Signing always happens on the user’s device. Keys never leave the device in plaintext and are never used for signing on servers. The enclave and a passkey only store an encrypted copy of the master key (the MasterDEK) for restore. They never sign transfers.

On Starknet that key controls an **audited OpenZeppelin account contract** (AccountUpgradeable v3.0.0). The audit covers OpenZeppelin, not Cavos. Cavos does not ship its own account implementation. There is no on-chain device-signer list and no on-chain social recovery. A new device restores the MasterDEK off-chain; it does not add a signer on-chain.

The backend can transport, sponsor, or submit a transaction. It does not hold the user authority required to move funds. Relayers and paymasters are not signers. Login selects which user this is. It never signs a transaction.

Keep `userId` stable. Addresses are looked up by `(userId, appId, chain, network)`. If your auth starts reporting an email where it used to report a primary key, those users land on a different wallet and nothing errors. If you already authenticate users (Clerk, Auth0, your own session), pass a stable `userId` as `identity`. Cavos login turns off: the modal is not mounted and `login()` throws. Pass `null` while your auth is loading and once the user signs out. Use an immutable primary key, not an email that can change.

## Never change appSalt after users exist

`appSalt` is required. It is the HKDF salt for the account key on every chain (stark key on Starknet, Ed25519 on Solana and Stellar). Changing it after users exist derives a different address that will not match the registry row. Those users see a new, empty wallet. The provider warns in development if this browser last connected with a different salt. Run the same checks yourself with `validateCavosConfig(config)` from `@cavos/kit`.

Register every callback URL in **Dashboard → App → Callback URLs**, one per line, matched exactly: scheme, host, path, no trailing slash, and no wildcards. OAuth fails with `redirect_uri is not registered for this app` when the callback URL is missing, including when the list is empty. Tunnel and preview domains each count as a separate origin.

Finish Google or Apple login in the same tab and origin that started it. The kit ties the callback to a one-time secret in `sessionStorage`. Symptoms and causes live in [troubleshooting](https://docs.cavos.xyz/docs/troubleshooting).

## Passkey after login

Signing up never asks for a passkey. Call `enrollPasskeyDefault()` after login, from settings, after the first transaction, or a banner. `secureStep` defaults to `'off'`.

```ts
const { enrollPasskeyDefault, approveDeviceWithPasskey, walletStatus, passkeySupported } =
  useCavos();

if (passkeySupported && walletStatus.isReady && !walletStatus.hasPasskey) {
  await enrollPasskeyDefault();
}

if (walletStatus.needsDeviceApproval && walletStatus.hasPasskey) {
  await approveDeviceWithPasskey();
}
```

The passkey holds an encrypted copy of the MasterDEK. Cavos stores the ciphertext; only the passkey can open it. A synced passkey that was added **can spend**. Frame it as restore, not 2FA. `deviceApproval: "passkey"` is one chain; use `deviceApproval: "enclave"` when Starknet, Solana, and Stellar share a login. See [passkeys](https://docs.cavos.xyz/docs/passkeys).

`walletStatus.recovery` is `{ protected: boolean; methods: ("passkey" | "social")[] }`. It starts `false` and flips once the lookup returns. Read it as “not known to be protected” during the first moments of a connect, not as “known to be unprotected.”

Do not wait for `isReady` before offering enrollment on a chain that is still `undeployed` if you only meant “this device has the key.” On Solana, `isReady` is true once this device holds the spend key. On Starknet and Stellar, `undeployed` still has the key; the on-chain account appears on first execute.

## Gas Sponsorship in Any Token

Users should not need a native token to start. Cavos frames this as **Gas Sponsorship in Any Token**. Sponsorship is chain-specific, not a universal gas tank.

| Adapter | Required configuration | Who pays |
|---|---|---|
| **Starknet** | App ID, network, app salt, identity, `paymasterApiKey` | Paymaster sponsors deploy and execute by default. After deploy, `fee: "self"` pays from the account’s own balance. A self-funded first execute is refused. |
| **Solana** | App ID, network, app salt, identity | Default is `fee: "self"` (the account pays SOL). Pass `fee: "sponsored"` so the hosted relayer is fee payer. Pass `fee: { token }` to settle the fee in a held token such as USDC. Arbitrary programs are allowlisted per app. |
| **Stellar** | App ID, network, app salt, identity | Hosted relayer sponsors reserves and fee-bump submission. `create()` creates the classic G account with 0 XLM. |

Add `paymasterApiKey` only when Starknet is in `chains`. A paymaster key on a chain that ignores it is a config error; the provider reports that in development. The current web SDK receives that value in browser code, so treat it as a **client-visible, app-scoped sponsorship credential**, never as an operator or treasury secret.

```ts
const { wallet } = useCavos();

if (wallet?.chain === "solana") {
  await wallet.execute(amount, dest);                            // account pays SOL
  await wallet.execute(amount, dest, { fee: "sponsored" });      // Cavos relayer pays
  await wallet.execute(amount, dest, { fee: { token: usdcMint } }); // user pays in USDC
}
```

## authError and needs-device-approval as first-class states

Do not hide wallet lifecycle behind a single spinner. Two states need their own UI: `authError` and `needs-device-approval`.

```tsx
import { useCavos } from "@cavos/kit/react";

function Wallet() {
  const { address, isAuthenticated, walletStatus, openModal, logout, isLoading, authError } =
    useCavos();
  if (isLoading) return <p>Connecting…</p>;
  if (authError) return <p>{authError}</p>;
  if (!isAuthenticated) {
    return <button onClick={openModal}>Sign in</button>;
  }
  if (walletStatus.needsDeviceApproval) {
    return <p>This device has no key yet. Restore the MasterDEK.</p>;
  }
  return (
    <div>
      {address} · ready={String(walletStatus.isReady)}
      <button onClick={logout}>Sign out</button>
    </div>
  );
}
```

Read `authError` from `useCavos()` and show it. Host consoles that JSON-serialize `Error` objects often print `{}` because `message` is non-enumerable; read the string off the error you caught.

When the registry has no row, this device computes a candidate address and claims it. A second device connecting later sees the existing address and enters `needs-device-approval` instead of creating a duplicate wallet. That is not on-chain approval. Restore the MasterDEK with a passkey or the [enclave](https://docs.cavos.xyz/docs/hardware-isolated-recovery).

| Status | Meaning | Can execute? |
|--------|---------|--------------|
| `undeployed` | Address derived but no on-chain account yet (Starknet, Stellar). | Yes. On Starknet the first execute deploys and runs atomically; on Stellar, call `create()` first. |
| `ready` | Account exists on-chain and this device holds the key. Native Solana is ready once this device has the spend key. | Yes |
| `needs-device-approval` | This device has no key yet. Restore the MasterDEK. | No |

**Do not require `walletStatus.isReady` before the first execute.** Both `undeployed` and `ready` wallets can send. Only `needs-device-approval` blocks transactions. An undeployed wallet can also sign messages.

Narrow on `wallet.chain` so TypeScript exposes the correct native method. On Solana and Stellar, call the wallet directly instead of the context’s `execute`. On Starknet, use the context’s `execute(calls)` for a multicall. It is sponsored by default.

```ts
const { wallet, execute } = useCavos();

if (wallet?.status === "needs-device-approval") {
  throw new Error("This device has no key yet. Restore the MasterDEK.");
}

if (wallet?.chain === "solana") {
  const txHash = await wallet.execute(1_000_000n, destinationAddress, { fee: "sponsored" }); // lamports
} else if (wallet?.chain === "stellar") {
  const txHash = await wallet.execute(1_000_000n, destinationAddress); // stroops
} else {
  const { transactionHash } = await execute([
    { contractAddress: TOKEN, entrypoint: "transfer", calldata: [to, amountLow, amountHigh] },
  ]);
}
```

For arbitrary execution, Starknet accepts multicalls, Solana exposes `executeInstructions`, and Stellar exposes `invokeContract`. See [wallet actions](https://docs.cavos.xyz/docs/wallet-actions).

## Testnet while developing

Ship the first integration against `network: "testnet"` and `environment: "development"` so test traffic does not drain the production gas pool.

`network` is the chain (testnet or mainnet). `environment` is the Cavos console environment (`development` or `production`). They answer different questions: which chain versus whose gas pool and API keys. Omit `environment` and the SDK uses `production`. See [environments](https://docs.cavos.xyz/docs/environments).

On Solana, an undeployed account is not the blocker: native Solana is `ready` once this device has the spend key. You can airdrop on testnet with `wallet.connection.requestAirdrop`. On Stellar testnet, friendbot funds the G… address. Starknet execute is paymaster-sponsored, so the user does not need ETH or STRK for the first invoke.

Confirm status per chain after `setChain`. One chain might be `ready` while another is `undeployed` or `needs-device-approval`.

```tsx
"use client";

import { CavosProvider } from "@cavos/kit/react";

export function Providers({ children }) {
  return (
    <CavosProvider
      config={{
        chains: ["solana", "stellar"],
        defaultChain: "solana",
        network: "testnet",
        environment: "development",
        appSalt: "my-app",
        appId: process.env.NEXT_PUBLIC_CAVOS_APP_ID,
      }}
      modal={{ appName: "My App" }}
    >
      {children}
    </CavosProvider>
  );
}
```

Passing `modal={{ appName: "My App" }}` mounts the hosted login modal. Omit `modal` if you will drive auth yourself. In the Next.js App Router, the file that renders `CavosProvider` needs `'use client'`. So does any component that calls `useCavos()`. Wallet state is not available during server rendering: the device key lives in the browser.

## Chain notes

Connect once, access every configured chain. `setChain(chain)` switches the active chain without remounting. Each chain has its own address, deployment status, and whether this device holds the key.

### Starknet: connect never deploys

Connect derives the address and unwraps the stark key. It **never deploys**. The first `execute` deploys the audited OpenZeppelin **AccountUpgradeable** (v3.0.0) and runs the user’s multicall atomically, in a single sponsored transaction. After that, status becomes `ready`. The audit covers OpenZeppelin, not Cavos.

Starknet connections require `paymasterApiKey`. Solana and Stellar use a relayer activated by `appId` instead.

### Solana: native Ed25519 system account

Solana is a plain Ed25519 system account: no custom on-chain program and no PDA. Connect unwraps the spend key. There is no deploy step. A system account appears when it first receives lamports. Connect does not airdrop SOL.

Fee is a per-call choice:

- omit `fee` or pass `fee: "self"`: the account pays SOL
- `fee: "sponsored"`: the Cavos relayer is fee payer (`appId` required)
- `fee: { token }`: settle the fee in a token the account holds

A co-signer cannot alter the instructions it signs. Sponsorship of extra programs is allowlisted per app, with a 1,000,000 CU cap.

### Stellar: classic G account

Stellar is a classic `G…` account, not a Soroban contract. Connect never creates the account. `wallet.create()` creates it (sponsored, starting at 0 XLM), and status becomes `ready`. A first `execute` also creates it, but its XLM payment fails with `op_underfunded` until the account holds XLM. The Ed25519 spend key is derived on the device with HKDF (`cavos-ed25519-stellar-v1`, salted by `appSalt`). `wallet.execute(amount, destination)` moves stroops. `wallet.invokeContract(...)` covers Soroban calls.

## React Native limits

React Native uses `@cavos/kit/react-native` (Expo Development Builds, EAS, or bare React Native; Expo Go is not supported). Minimum platforms are iOS 16 and Android 9 (API 28).

Google and Apple login work through the registered deep or universal link. **Telegram, email, and GitHub are not available** on React Native: that build cannot verify the enclave attestation those flows need. The native `providers` type still lists `"email"`, but the flow is not implemented. `'github'` and `'telegram'` are not accepted.

Telegram on web remains optional OAuth via `oauth.telegram.org`, not a Mini App. Do not expect a Telegram Mini App bridge in the kit.

This guide stays on web React for the snippets above. Native setup, `redirectUri`, `rpId`, and `minimumKeySecurity` live in the [React Native docs](https://docs.cavos.xyz/docs/react-native).
