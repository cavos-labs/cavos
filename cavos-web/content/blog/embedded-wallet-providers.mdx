An [embedded wallet](/embedded-wallet) lives inside your application. Wallet-as-a-service is the commercial name for the same job: provision an on-chain account from a login, sign in your UI, and skip the browser-extension install. The words do not pick a key model. This guide is the listicle for teams comparing **embedded wallet providers**, **embedded wallet solutions**, and **embedded wallets as a service** — pricing, chains, and who can produce a signature.

Cavos, LLC is a software and SaaS company. Positioning for Cavos comes after the table is fair. If the honest answer is another vendor, that is the answer. One-to-one pages live under [compare](/compare). Teams leaving Privy specifically can start at [Privy alternatives](/privy-alternatives).

## What an embedded wallet (and wallet-as-a-service) is

The user signs in the way they already do. The SDK looks up or creates an on-chain account for that identity. Approval stays in the product. There is no seed phrase in the happy path and no second program to install.

That is **where the wallet appears**. It is not a custody claim. An embedded wallet can be device-native self-custody, MPC shares, a remote enclave, or a delegated TEE. A wallet-as-a-service API can sit at any of those layers. Turnkey is closer to signing infrastructure. Privy, Dynamic, Magic, Web3Auth, and Cavos ship a finished login-to-signature path. Ask who can move funds without the user present. The [custody](/custody) page is the control test; this page is the shortlist.

## How to evaluate providers

Write the answers down before you read a pricing page.

- **Custody / key model.** Device-native, MPC, TEE or HSM, remote enclave. Who holds a share, a wrap, or a credential that can authorize a spend.
- **Chains.** Which networks are native (account model, fees, signatures) versus a reused EOA-shaped key. Cavos is [Starknet](/embedded-starknet-wallet), [Solana](/embedded-solana-wallet), and [Stellar](/embedded-stellar-wallet) only.
- **Gas sponsorship.** Whether first transactions work with an empty native-token balance, and whether that feature is on the public plan or enterprise-only.
- **Auth methods.** Email, social, SMS, passkeys, bring-your-own JWT. Login selects the user. It should not, by itself, be the spend key — unless you chose a hosted model on purpose.
- **Pricing.** Units differ: wallet creates, monthly active users, monthly active wallets, signatures, volume. A cheap free tier with a tight MAU cap is not the same as a flat wallet-create allowance.
- **Lock-in.** Can the user export a key? Can you restore the same address on another vendor? Addresses are derived differently. Migration is a project. Confirm export, import, and what happens if you cancel the subscription.

The category has consolidated. Stripe acquired Privy in 2025. Fireblocks acquired Dynamic in 2025. Consensys acquired Web3Auth in 2025 and now ships it as MetaMask Embedded Wallets. In 2026 Payward, the parent of Kraken, agreed to acquire Magic Labs’ wallet-as-a-service business. Acquisition is a vendor-risk and roadmap input. It does not change who can produce a signature.

## Privy vs Turnkey vs Dynamic

Search Console shows people asking this as a scope question, not a feature checklist.

**Privy** is a finished embedded wallet and authentication product. The public pricing page lists unified login (email, SMS, socials, passkeys), embedded wallets, and wallet connectors for EVM and Solana. Keys are managed in Privy’s TEE infrastructure. Privy’s own docs say neither Privy nor the application sees the user’s keys on the non-custodial path; secrets are reconstituted in a secure environment under the user’s control. In 2026 Privy also added optional custodial wallets, starting with Bridge, chosen per wallet. Use Privy when you want one vendor for login, an in-app wallet, and connecting wallets users already hold — especially on EVM.

**Turnkey** is key-management infrastructure. Private keys persist as ciphertext and decrypt only inside AWS Nitro Enclaves. Custody is determined by who holds the credentials that can authorize the enclave: the end user (non-custodial), your API key (custodial), or both under policy (hybrid). Auth includes passkeys, OAuth, email, and API keys. Gas sponsorship is listed on the Enterprise plan. Use Turnkey when you are building a wallet or custody product and want policy, quorums, and server-side signing primitives. Privy vs Turnkey is usually build-versus-buy.

**Dynamic** is strongest as a unified login and wallet-connection layer that also ships embedded wallets. Connecting existing external wallets is a core capability. Embedded wallets use TSS-MPC: a user share on the device and a server share that participates in signing inside a TEE. Dynamic’s public docs say the full private key is never constructed, wallets are end-user owned, and export is supported. Native embedded-wallet chains on the public docs include EVM, Solana, Bitcoin, Sui, TON, Stellar, Tempo, and Arc. Gasless transactions on EVM and Solana are listed as an Enterprise feature. Use Dynamic when users already hold wallets you must connect, or when you want that connector surface plus an embedded fallback. Privy vs Dynamic is usually provision-versus-connect.

None of those three is “the Starknet / Solana / Stellar device-native SDK.” That is a different product shape.

## When Cavos is the right pick — and when it is not

Cavos is an [embedded wallet](/embedded-wallet), not an extension, and not a connector.

Signing keys are created and used on the user’s device. Cavos cannot see them, sign with them, or move funds. Login produces a stable identity for a registry lookup; it never signs a transaction. There is no MPC. There is no hosted spend key.

On Starknet the on-chain account is an **audited OpenZeppelin AccountUpgradeable** v3.0.0, controlled by one stark key derived from the wallet’s MasterDEK and app salt. Cavos does not ship its own account implementation. There is no on-chain device-signer list and no on-chain social recovery. A new device restores the MasterDEK off-chain with a passkey or an opt-in AWS Nitro Enclave; it does not `add_signer`. Execution is paymaster-sponsored. Connect does not deploy — the first execute deploys and runs atomically.

Solana and Stellar are native adapters, not EVM compatibility. Solana provisions a native Ed25519 system account; a relayer co-signs as fee payer. Stellar provisions a classic G… account so existing tools already understand the address; the relayer can sponsor reserves and fee-bumps. Both restore the same MasterDEK on a new device rather than adding a second on-chain signer.

Auth is hosted Google, Apple, or email, or an identity you pass in from your own stack. The React path is `@cavos/kit`; mobile is `@cavos/kit/react-native`. The [React integration guide](/blog/how-to-add-an-embedded-wallet) and the [Cavos docs](https://docs.cavos.xyz/docs/quickstart) are the install. [Pricing](/pricing) publishes the free 1,000 wallet creates, Essential at $59/mo, and Complete at $139/mo with enclave recovery.

**Choose Cavos** when the user should never see a wallet picker, the chain is Starknet, Solana, or Stellar, and the review requires that the vendor cannot reconstruct a signing key.

**Choose someone else** when the product is EVM-first, when you must connect MetaMask or WalletConnect, when you need server-side signing or organizational quorums as a product feature, or when you want a single vendor across dozens of EVM networks. Cavos does not inject into `window.ethereum` and does not speak WalletConnect. Those are honest gaps, not a smaller feature set.
