---
title: Recovery
description: The four ways a Cavos user regains access to their wallet after losing a device — and which ones to offer.
---

A Cavos wallet is controlled by keys that live on the user's devices and never
leave them. That is the point, and it is also the risk: **a device that is lost,
wiped, or replaced takes its key with it.**

So the account is built to recognize more than one authority. Recovery is the
work of setting up a second one *before* it is needed, because none of these can
be arranged after the fact.

## The four paths

| Path | The user needs | Best for | Cost |
|---|---|---|---|
| [**Multi-device**](/docs/multi-device) | Another signed-in device | Users who already have a second device | Nothing to set up |
| [**Passkeys**](/docs/passkeys) | Face ID / Touch ID / PIN | Almost everyone | One prompt **after** login (`enrollPasskeyDefault`) — never during OAuth |
| [**Recovery codes**](/docs/recovery-codes) | A code they stored | Starknet, and grandfathered Stellar | The user must keep a secret |
| [**Hardware-isolated recovery**](/docs/hardware-isolated-recovery) | To sign in again with Google / Apple / email | Solana, Stellar, and Starknet | Opt-in per environment; the enclave wraps the MasterDEK (Solana/Stellar) or schedules `add_signer` (Starknet) |

The first two answer *"I still have something."* The last two answer *"I have
nothing."* A serious app wants at least one of each.

## What to offer

**Start with a passkey or the enclave — not both as the same `deviceApproval`.**
`deviceApproval: "passkey"` is one chain, and a passkey that was added can open
the Solana/Stellar wallet. `deviceApproval: "enclave"` wraps the MasterDEK for
every native chain in the session. Signing up never asks for a passkey; call
`enrollPasskeyDefault()` when you want one.

**Add a way back from nothing.** On Solana/Stellar that is the enclave (sign in
again) or a passkey the user added. Recovery codes do **not** restore native Solana.
On Starknet, recovery codes and the enclave's restricted `add_signer` still
apply.

**Do not rely on multi-device alone** for native Solana: there is no second
on-chain signer. A second phone unwraps the same DEK.

<Callout type="warn">
If a user loses every device and every factor, and none of the above was set up,
**Cavos cannot restore access.** No support ticket recovers that wallet, because
no Cavos key can. This is what self-custody costs, and it is the reason to set up
a second authority during onboarding rather than when it is needed.
</Callout>

## What Cavos never does

None of these paths gives Cavos a hot key that can move funds in production
relaying. The enclave may wrap a MasterDEK (Solana/Stellar) or hold a Starknet
authority that can only schedule `add_signer`.

Hardware-isolated recovery is the only path that introduces a party beyond the
user and the chain, and it is deliberately bounded: see
[Why this is still self-custodial](/docs/hardware-isolated-recovery#why-this-is-still-self-custodial).

## Per-chain detail

Each adapter implements these with the primitives its chain offers.
[Recovery codes](/docs/recovery-codes) has the per-chain restore paths, and
[Hardware-isolated recovery](/docs/hardware-isolated-recovery#what-the-chain-enforces)
covers what each chain enforces on the recovery authority.
