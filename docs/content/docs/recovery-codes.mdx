---
title: Recovery codes
description: A stored code that restores grandfathered Stellar wallets. Starknet, Solana, and native Stellar restore the MasterDEK instead.
---

Cavos cannot reset a wallet or authorize a replacement device by itself. The
recovery code costs nothing and involves no server: a high-entropy code,
generated on a device the user already controls, which derives a backup
authority the account recognizes. Today that applies to grandfathered Stellar
wallets only.

The trade-off is the one every code-based scheme has — the user has to keep it.
For recovery that works by signing in again instead, see
[Hardware-isolated recovery](/docs/hardware-isolated-recovery).

## Recovery capabilities

| Chain | Recovery code role | Restore path |
|---|---|---|
| **Starknet** | **Not used.** Native accounts have one stark key | Enclave login or `approveDeviceWithPasskey()` |
| **Solana** | **Not used.** Native accounts have one spend key | Enclave login or `approveDeviceWithPasskey()` |
| **Stellar (enclave)** | Same MasterDEK wrap as Solana | Sign in again |
| **Stellar (grandfathered)** | Extra ed25519 Horizon signer | Reconnect, then `approveThisDeviceWithRecovery(code)` |

## Set up once

Generate a code on a connected device, show it once, and ask the user to store it
offline:

```ts title="TypeScript"
import { generateRecoveryCode } from "@cavos/kit";

const code = generateRecoveryCode();
await wallet.setupRecovery(code);

// Display `code` once. Never send it to analytics, logs, or your backend.
```

`setupRecovery` is chain-specific. Starknet, Solana, and native Stellar have
nothing to register and ignore it. Only grandfathered Stellar wallets use it.

<Callout type="warn">
Anyone with the recovery code may be able to restore wallet authority. Treat it
like a private key: never log it, never email it in plaintext, and never persist
it in application storage.
</Callout>

## Restore Starknet and Solana

There is no recovery-code restore. Native accounts restore the MasterDEK:

```ts title="TypeScript"
// Enclave: the same Google/Apple/GitHub/email login on the new device unwraps the DEK.
// Passkey:
const { approveDeviceWithPasskey } = useCavos();
await approveDeviceWithPasskey();
```

## Restore Stellar

**Native DEK:** do not call `approveThisDeviceWithRecovery`. Sign in again
(enclave) or `approveDeviceWithPasskey()`.

**Grandfathered:**

```ts title="TypeScript"
import { Cavos } from "@cavos/kit";

const session = await Cavos.connect({
  chains: ["stellar"],
  defaultChain: "stellar",
  network: "testnet",
  identity: { userId: user.id, email: user.email },
  appSalt: "my-app",
  appId: process.env.NEXT_PUBLIC_CAVOS_APP_ID,
});

const wallet = session.wallet("stellar");
if (
  wallet.chain === "stellar" &&
  wallet.status === "needs-device-approval" &&
  !wallet.nativeDek
) {
  await wallet.approveThisDeviceWithRecovery(code);
}
```

The recovery factor is itself a Horizon signer. It `setOptions` the fresh
device's ed25519 key onto the account.

## Product guidance

- Encourage a synced passkey or the enclave before relying on a recovery code.
- Verify recovery on physical iOS and Android devices before production release.
- Treat the code as one factor among several, not the plan. Most users will not
  keep it, which is the problem [hardware-isolated
  recovery](/docs/hardware-isolated-recovery) exists to solve on Starknet,
  Solana, and native Stellar. Grandfathered Stellar wallets still use the code
  (or a synced passkey extra signer) as the way back from nothing.
- If the user loses every device and every recovery factor, and — on Starknet,
  Solana, or native Stellar — neither the enclave nor a passkey was enrolled,
  Cavos cannot restore access. That is the cost of the guarantee, not a gap in
  it.

See [Multi-device](/docs/multi-device), [Passkeys](/docs/passkeys), and the
selected [chain guide](/docs/chains).
