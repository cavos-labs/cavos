title: Quickstart
description: Install @cavos/kit, connect to one or more chains, and execute your first sponsored transaction.
---

The onboarding contract is shared across every Cavos
[embedded wallet](https://cavos.xyz/embedded-wallet) adapter: authenticate,
connect, then execute. Connect derives addresses and checks deployment status
but **never deploys**. The first `execute` triggers deployment atomically with
the user's operation.

## 1. Install

```bash title="Terminal"
npm install @cavos/kit@^0.5.0
```

Create an app in the [Cavos dashboard](https://cavos.xyz/dashboard) and copy its
App ID. Starknet sponsorship also requires a paymaster API key. The current web
SDK receives that value in browser code, so it must be treated as a
**client-visible, app-scoped sponsorship credential**, never as an operator or
treasury secret. Before production, bind and limit it by app, environment,
origin, rate, and spend in the sponsorship service.

## 2. Connect

Connect derives the address for every configured chain and checks whether the
account exists on-chain. It **never deploys** Starknet or Stellar. Deployment
happens lazily on the first `execute` call. Native Solana is `ready` once this
device has the spend key.

This Solana example needs only the public App ID in the browser:

```ts title="TypeScript"
import { Cavos } from "@cavos/kit";

const session = await Cavos.connect({
  chains: ["solana"],
  defaultChain: "solana",
  network: "testnet",
  appSalt: "my-app",
  identity: {
    userId: user.id, // stable, immutable identifier
    email: user.email,
  },
  appId: process.env.NEXT_PUBLIC_CAVOS_APP_ID,
});

console.log(session.address);  // the address for the default chain
console.log(session.status);   // Solana: "ready" | "needs-device-approval"
```

The returned session is the default chain's wallet augmented with multi-chain
methods. `session.wallet("solana")` returns the Solana wallet;
`session.chainStatus("solana")` returns its status.

### Status values

| Status | Meaning | Can execute? |
|--------|---------|--------------|
| `undeployed` | Address derived but no on-chain account yet. | Yes: first execute deploys + runs atomically. |
| `ready` | This device holds the account key. | Yes |
| `needs-device-approval` | The wallet exists but this device holds no key. | No: route to [device approval](#5-handle-device-approval). |

<Callout type="info">
**Lazy deploy**: An `undeployed` wallet can sign messages (`signMessage`) and
execute. The first `execute` call deploys the account and runs the user's
operation in a single sponsored transaction. No separate deploy step is needed.
</Callout>

## 3. Execute

Narrow on `wallet.chain` so TypeScript exposes the correct native method. Both
`undeployed` and `ready` wallets can execute.

```ts title="TypeScript"
const wallet = session.wallet("solana");

// Only needs-device-approval must be handled differently
if (wallet.status === "needs-device-approval") {
  throw new Error("This device must be approved first");
}

if (wallet.chain === "starknet") {
  const { transactionHash } = await wallet.execute(calls);
} else if (wallet.chain === "solana") {
  // lamports; the account must hold them. `fee: "sponsored"` makes the relayer pay the fee.
  const signature = await wallet.execute(1_000_000n, solanaRecipient, { fee: "sponsored" });
} else if (wallet.chain === "stellar") {
  const hash = await wallet.execute(1_000_000n, stellarRecipient); // stroops
}
```

When the account is `undeployed`, `execute` deploys it first, then runs the
operation atomically, in a single sponsored transaction. After the first
execute, status becomes `ready`.

On Solana the account pays its own fee unless you pass `fee: "sponsored"`; on
Starknet and Stellar sponsorship is the default.

For arbitrary execution, Starknet accepts multicalls, Solana exposes
`executeInstructions`, and Stellar exposes `invokeContract`. Each path has
adapter-specific validation and sponsorship rules.

## 4. Configure the selected adapter

| Adapter | Required configuration | Sponsored execution |
|---|---|---|
| **Starknet** | App ID, network, app salt, identity, `paymasterApiKey` | Paymaster sponsors deploy and execute. |
| **Solana** | App ID, network, app salt, identity | The account pays its own fee by default; with `fee: 'sponsored'` the hosted relayer is fee payer, and arbitrary programs are allowlisted per app. |
| **Stellar** | App ID, network, app salt, identity | Hosted relayer can sponsor reserves and fee-bump submission. |

Use the dedicated [Starknet](/docs/starknet), [Solana](/docs/solana), or
[Stellar](/docs/stellar) guide for production configuration. The matching
product pages are the
[Starknet](https://cavos.xyz/embedded-starknet-wallet),
[Solana](https://cavos.xyz/embedded-solana-wallet), and
[Stellar](https://cavos.xyz/embedded-stellar-wallet) landings.

## 5. Handle device approval

`status === "needs-device-approval"` means the identity already owns a wallet
but this device holds no key yet. Do not create a second wallet. Restore the
MasterDEK with a [passkey](/docs/passkeys) the user added or with
[hardware-isolated recovery](/docs/hardware-isolated-recovery) (sign in again).
See [Multi-device](/docs/multi-device) for the flow.

<Callout type="info">
Starknet, Solana, and Stellar restore the same way: the MasterDEK is
unwrapped on the new device. Use the high-level wallet methods and follow the
selected adapter's capability notes.
</Callout>

## More than one chain

Connect once, access every configured chain. The session provides wallets for
all chains without re-authenticating:

```ts title="TypeScript"
const session = await Cavos.connect({
  chains: ["solana", "stellar", "starknet"],
  defaultChain: "solana",
  network: "testnet",
  appSalt: "my-app",
  identity,
  appId: process.env.NEXT_PUBLIC_CAVOS_APP_ID,
  paymasterApiKey: process.env.NEXT_PUBLIC_CAVOS_PAYMASTER_API_KEY, // Starknet only
});

// Access any chain's wallet
const solana = session.wallet("solana");
const stellar = session.wallet("stellar");
const starknet = session.wallet("starknet");

// Check status per chain
console.log(session.chainStatus("solana"));   // "undeployed" | "ready" | "needs-device-approval"
console.log(session.chainStatus("stellar"));
console.log(session.chainAddress("stellar")); // G… address

// Execute on Stellar (works even if undeployed: first execute creates the account)
if (stellar.chain === "stellar" && stellar.status !== "needs-device-approval") {
  await stellar.execute(10_000_000n, "GDEST...");
}
```

Each chain has its own address, derived from the same identity. Deploy happens
independently per chain on first execute. One login, multiple wallets, no
re-authentication.

## React

For UI applications, use the bindings from `@cavos/kit/react`:

```tsx title="app/providers.tsx"
import { CavosProvider } from "@cavos/kit/react";

export function Providers({ children }) {
  return (
    <CavosProvider
      config={{
        chains: ["solana", "stellar"],
        defaultChain: "solana",
        network: "testnet",
        appSalt: "my-app",
        appId: process.env.NEXT_PUBLIC_CAVOS_APP_ID,
      }}
      modal={{ appName: "My App" }}
    >
      {children}
    </CavosProvider>
  );
}
```

The provider gives you `setChain(chain)` to switch the active chain without
re-mounting or re-authenticating. See [React](/docs/react) for the full guide.

Continue with [React](/docs/react), [React Native](/docs/react-native), or the
full [API reference](/docs/api-reference). The
[React integration guide](https://cavos.xyz/blog/how-to-add-an-embedded-wallet)
covers the same install on the marketing site. If you are deciding between an
in-app wallet and a browser extension, read
[embedded wallet vs browser extension](https://cavos.xyz/blog/embedded-wallet-vs-browser-extension).

If something does not behave as described here, [Troubleshooting](/docs/troubleshooting) lists the symptoms integrators hit most and what actually causes them.
